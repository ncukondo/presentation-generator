# スライドデザイン原則

このプレゼン生成器で出力するスライドに共通して適用するデザインルール。
`lib/render.ts` でレイアウト（layout）を書く時、QA エージェントが画像をチェックする時、この文書が判定基準になる。

原則は「優秀なデザイナが守る普遍則」ではなく「**このリポジトリで**いま守るべき運用ルール」として書く。曖昧な標語より、機械的に違反を検出できる具体値を優先する。

**最上位原則: 聴衆に内容が伝わることを最優先する。** 以下の規則はすべてそのための手段。
規則を満たすために伝達に必要な情報を削るのは本末転倒であり、その場合はレイアウトを調整・新設する。
内容を削るのは、それにより簡潔になって伝わりやすくなる場合のみ。

## 1. 配色の運用

### 役割を固定する — 色に「意味」を持たせる

1つの色 = 1つの役割。順番や装飾で色を割り振らない。
具体色は**テーマ（`slides.yaml` の `theme:` / `lib/themes.ts`）で差し替わる**ので、コードでは hex 直書きせず役割名（`C.xxx`）で参照する。既定 preset は `slate`。下表の hex は分かりやすさのため preset `blue` を例に示す（役割名で参照していれば preset 差し替えで一括再配色される）。

| 役割 | 参照（例: blue preset） | 使う場所 |
|------|--------|---------|
| **Primary** | `C.primary` (例 #1E88E5) | タイトルバー・章見出し・ボディ強調の主役 |
| **Accent** | `C.accent` (例 #FF9800) | CTA・重要告知・アンダーライン。**1スライドに最大1箇所** |
| **Text** | `C.text` (例 #37474F) | 本文。真黒は避ける |
| **MidGray** | `C.midGray` / `C.darkGray` | 補助情報・引用文字 |
| **Warm BG** | `C.warmBg` (例 #FFF9F2) | スライド地色 |
| **Card pastel** | `C.cardBlue` etc. | セマンティックに色分ける時**だけ**使う |
| **Step colors** | `C.step1..7` | 同一画面に並ぶ「区別が意味を持つ」要素（7ステップ・複数カテゴリ）専用 |

### 配色の禁止事項

- ❌ カードや番号を**順番で色分けしない**。内容が「並列3項目」なら全部同色（primary 濃淡・モノクロ）で揃える。
- ❌ 1枚のスライドで**6色以上**の顕色（primary/accent/step カラー）を使わない。pastel 背景は色数にカウントしない。
- ❌ 真っ赤 (#E53935) や真っ緑 (#43A047) のベタ塗りをカードヘッダに使わない。**ヘッダは primary または step カラーの濃いもの**に統一し、意味的に「警告・成功」の文脈でしか彩度の高い赤緑を出さない。
- ❌ 青背景の上に `C.accent` の小さい文字を置かない（コントラスト 2.5:1 以下）。

### 優越比 (dominance)

1スライドの面積比: primary 60–70% / 中立色（地色+text）20–30% / accent 5% 以下。
「全部色鮮やか」は散漫に見える。

## 2. 最小フォント・タイポグラフィ

### 最小サイズ

| 種別 | 最小 pt | 備考 |
|------|---------|------|
| 本文・カード内文 | **22pt** (`FS.body`) | これを下回らない |
| 補足・引用・注記 | **18pt** (`FS.micro`) | 画面の 5% 以下の面積に限る |
| タイトル | 28pt (`FS.slideTitle`) 以上 | |
| セクション見出し | 24pt (`FS.heading`) 以上 | |

> **ルール**: 本文で 20pt 以下を使いたくなったら、まず冗長な表現を簡潔にできないか、次にレイアウト（列数・幅・layout 種別）を変えられないかを検討する。伝達に必要な情報を削ってまで既存レイアウトに収めない。最小サイズを割るのは例外扱い。

### フォント

日本語は `Meiryo`、英語は `Arial`。1スライド内でフォントを3つ以上混在させない。

### 折り返し禁止ゾーン

- カード幅が「**1行に最低でも全角15文字**」入らない場合、そのレイアウトは採用不可。列数を減らすかレイアウトを変える。テキストを削るのは、簡潔になって伝わりやすくなる場合のみ。
- 縦書きのような「1文字ずつ改行される」折返しが出たら**即修正**。
- **孤立行（orphan）**: 最終行が全角1〜3文字しか無い折返し（例「…タイト」/「ル」）は不可。
- 英数字トークン（`GPT-4o` 等）を途中で割らない。句読点 `。、）」` を行頭に出さない（禁則処理）。
- タイトルは2行以内。3行超は言い回しを簡潔にする。必要な情報が落ちるなら、サブタイトルや本文に移す。
- **狭いカード（全角7〜8字/行）で日本語が語の途中で割れる**時（「経／路」「コー／ディング」等）は、助詞・文節の切れ目に**手動 `\n`** を入れて自然な改行にする。自動バランサは行を均等割りして語中で切ることがあり、手動 `\n` は尊重される。
- 固有名詞・組織名は**一区切り**を保つ（例「卒後臨床研修・キャリア形成支援センター」を途中改行しない）。
- `[wrap] too-narrow` は列幅ヒューリスティックの警告で、**実際に語が割れているかは出力PNGを目視で最終判断**する（警告が残っても語が割れていなければ可）。

> ビルド時に `lib/text-metrics.ts` が禁則・自然な区切りでテキストを自動バランスし、orphan を解消する。`\n` 挿入で直せないもの（幅不足・縦はみ出し・分割不能な長語）は `[wrap] RECOMMEND` と `wrap-report.json` に改修推奨として出る。

## 3. 余白・レイアウト

### 絶対マージン

- スライド端からコンテンツまで **0.5in 以上** (`MARGIN.left/right` ≥ 0.6in 遵守)
- カード間の隙間 **0.2in 以上**
- 要素同士の最小ギャップ **0.1in**（これ未満は「重なり」と判定）

### 垂直バランス

- 「上半分だけ使って下が空白」は禁止。**コンテンツ領域の上下70%以上**に要素を分布させる。
- 下部にスペースが余るなら、フォントを上げる・カードを縦に伸ばす・セクションを増やす・レイアウトを変える。

### 中央偏り禁止

- 全要素が画面中央に寄って左右に大きな余白、というレイアウトは NG。**コンテンツ領域の 80% 以上の幅**を使う。
- 例外: タイトルスライド・全画面引用（hero-quote）のみ。

### カード内テキストが左に偏る時

- 短いテキストがカード幅に対して左に寄って見える時は、**テキストは左揃えのまま（行頭が揃い読みやすい）、その内容幅のブロックをカード内で水平中央に置く**。純粋な中央揃えは行頭が不揃いで読みにくいことがあるので、まずこの「左揃え＋ブロック中央」を検討する。
- ブロック幅は**最長行の実幅に合わせる**（広すぎるとブロック内で再び左偏りになる）。

## 4. レイアウトの選定とバリエーション

### 選定手順 — 内容が先、レイアウトは後

レイアウトは「既存の一覧から選ぶ」のではなく、次の順で決める。

1. **内容を検討する。** このスライドで聴衆に何を理解してほしいか、その内容の構造は何か
   （並列・順序・対比・流れ・包含・段階・数値・画面操作・単一の事実）。
2. **理想像を描く。** その内容を聴衆に伝えるのにふさわしい見せ方を、既存 layout に縛られずに考える
   （「同じ起点から2経路に分かれ、見た目は同じで中身が違うことを見せたい」など）。
3. **既存 layout に当てはまるものがあれば流用する。** 理想像に合う layout が `docs/layouts.md` に
   あれば使う。「近いから」で妥協して内容を layout に合わせて削らない（最上位原則）。
4. **無ければ新設または変更する。** `lib/render.ts` に layout を足す、既存 layout の列数・幅・
   要素を変える。ためらわない。新設した layout は `lib/validate.ts` と `docs/layouts.md` にも登録する。

### 内容の構造と layout の対応（目安）

| 内容の構造 | まず検討する layout |
|-----------|------|
| 並列の 2-4 項目 | `number-cards`（順序が無ければ `badge: none` かアイコン） |
| 順序のある工程 | `steps`（一覧）＋ `step-detail`（画面操作の各段階） |
| 2 者の対比・定義＋事例 | `split` / `compare-paths`（同じ起点からの 2 経路） |
| データ・情報の行き先 | `data-flow` |
| 連続的な段階・包含関係 | `spectrum` / `nested-layers` |
| 反復するプロセス | `agent-loop` |
| 数値の推移・比較・割合 | `chart` / `usage-bars` / `big-stat`（1-3 個の KPI） |
| 表形式の比較 | `table` |
| 図版・スクリーンショットを大きく | `figure` / `demo`（動画） |
| リスクと対策 | `risks` |
| 散文的な列挙（序論・考察・まとめ） | `bullets` |
| 1 枚まるごと一文 | `statement` |
| 章扉・締め | `section` / `closing` |

**同じレイアウトを3枚以上連続で使わない。** ステップ詳細のように性質上同一になる場合を除き、意識的に切り替える。

各スライドは**画像・アイコン・図形のいずれか1つ以上**を含めること（純テキストだけのスライドは作らない）。

## 5. アイコン・図の扱い

### 図・アイコンは「理解を補足する」ために置く。必ず内容に合ったものを使う

- **関係・流れ・比較・段階・包含は、文章で説明するより図で示す。** 該当する図解 layout が
  あれば優先して使う（`data-flow`＝データの行き先、`compare-paths`＝同じ起点からの2経路、
  `usage-bars`＝カテゴリ別の割合、`spectrum`＝連続的な段階、`nested-layers`＝包含関係、
  `agent-loop`＝反復ループ、`chart`＝数値の推移・比較）。無ければ layout を新設する（最上位原則）。
- **画面操作は `step-detail` のスクリーンショットに注釈（`rectAnnotations` / `arrows` /
  `textAnnotations`）を付けて「どこを見るか」を示す。** 注釈の無いスクリーンショットは
  聴衆が探すことになる。
- **アイコンは内容の比喩として選ぶ。** MDI から意味で探す（例: 文献検索=`book-search-outline`、
  選定=`filter-outline`、データ抽出=`table-search`、統計解析=`chart-box-outline`、
  執筆=`file-document-edit-outline`、投稿=`send-outline`、処理時間=`timer-outline`、
  導入=`download-outline`）。**合うものが無ければ置かない。** 見た目のために似た絵を流用しない。
- **レンダラは既定アイコンを持たない。** 内容を知らない側が決めたアイコンは必ず装飾になる。
  アイコンは `slides.yaml` 側で内容に合わせて指定する（`steps[].icon` / `items[].icon` 等）。
- 図版（`figure` / `split` の `image`）には**何を見るべきかが分かる caption** を付ける。
  図の中の該当箇所を示せるなら accent 色で強調する。

### サイズと配置の下限

- アイコン単体の最小サイズ **0.6in**。カード内の小さいフットプリントに置く時でも **0.4in** を下回らない。
- アイコンは「内容の比喩」であるべき。**装飾だけのアイコンを置かない**（slide02 の脳・時計・ヘッドフォン問題）。内容に合致するアイコンが無いなら置かない方がマシ。
- ステップ番号の丸アイコン (`addStepNumber`) は最小 **0.5in**。7ステップ並べる場合は 0.4in まで許容。
- **連番（01,02…）は順序を意味する時だけ**使う。並列カテゴリ（透明性/traceability/再現性 のような対等な項目）には連番を付けない。意味を足せる概念アイコンに置き換える（例: 透明性=`eye-outline`, traceability=`map-marker-path`, 再現性=`repeat`, 文献検索=`book-search-outline`, 量的分析=`chart-bar`, 質的分析=`comment-quote-outline`, 執筆・査読=`file-document-edit-outline`）か、いっそ外す。空の番号バッジは装飾ノイズ。

## 6. コントラスト要件

WCAG AA 基準を目安にする。

- 本文 vs 背景: **4.5:1 以上**
- 大きな文字（24pt 以上）・アイコン vs 背景: **3.0:1 以上**
- **青系の濃い背景に白以外の色で文字を置かない**。特に `accent` の橙は青背景でコントラスト不足（slide01 発表者名・slide14 補足メッセージの事例）。
- **引用（in-text）は `C.darkGray` を使う**。`C.midGray` は白背景で 3:1 を下回り読めない。引用は本文と区別しつつ「読める」濃さを保つ。
- 引用はカード**下端に固定**して配置し、本文の行数で上下に揺れて不揃いにならないようにする。

## 7. 一貫性のビジュアル要素 (repeat element)

プレゼン全体で**1つの署名的なビジュアル要素**を繰り返し、統一感を出す。このリポジトリでは:

- **上部に primary 青の帯 + 下に accent 橙のアンダーライン** を全コンテンツスライドに適用
- カードは **角丸 0.08in の rectRadius** で統一
- 番号は **円形塗りの step カラー** で統一

新レイアウトを追加する時もこの要素を流用する。

## 8. コンテンツの衛生 (content hygiene)

- プレースホルダ文字列（`xxxx`, `TODO`, `lorem ipsum`, `ここに記入`, `〜をここに記載`）が**出力画像に残っていたら失格**。QA チェックで検出する。
- `cite()` が空文字列や未定義を受けた場合、その文字列自体を出さない（`(@)` 表示禁止）。
- References スライドが空になる状態は「引用未使用」または「引用キー未解決」のサインなので、warning を出す。

### 要素は「意味を足す時だけ」置く（今回の振り返りの核）

- **他の要素の言い換えに過ぎない補足要素は、要素ごと削除する。** 対象は `subtitle` / `banner` /
  `note` / `footnote` / `eyebrow` / `desc` / カード `body` など、レイアウト上「任意」のパーツ全部。
  タイトル・見出し・本文の要約や同義反復、ナレーションの繰り返しにしかなっていないなら、
  短くするのではなく**空欄にして要素そのものを消す**（レンダラは省略時に残り要素を詰めて配置する）。
  これは作成時だけでなく、既存デッキの点検時にも適用する。
- **サブタイトルはタイトルに情報を足す時だけ置く**。タイトルの言い換え・同義反復なら削除する（不可例「生成AIは…どの段階にも入ってきている」に対し「文献検索から執筆まで広く使われている」）。残すなら**対象領域の限定・根拠の付加など新情報**を入れる（可例「医療者教育の研究でも、活用が広がっている」＋スコーピングレビュー引用）。
- 1カード内に複数行を置く時、それらが**意味的に対等**なら、太字＋グレーのような主従の見た目を付けない。等価に見せる（同一スタイル、必要なら中黒）。主従の体裁は本当に主従がある時だけ。
- 装飾的な番号・アイコン・帯は「無いと困るか」で判定する。困らないなら外すか、意味を持つ要素に置き換える。

## 9. 違反時の判断フロー

QA で違反が見つかった場合、まず **「聴衆に伝わるために何が必要か」** を確認し、以下の順で検討する:

1. **冗長の除去**: 同義反復・言い換え・装飾的な要素・不要な修飾を削る。**簡潔になって伝わりやすくなる場合のみ**削る。
2. **レイアウト変更・新設**: 別レイアウトに差し替える（3カラム→2カラム、grid→row）、列数・幅・行数を変える、
   既存で表現できなければ `lib/render.ts` に layout を新設する。**ためらわない**。
3. **フォント/余白調整**: 最後の手段。最小値を割る調整はしない。

判断基準は「削った結果、聴衆の理解が変わらないか」。変わらないなら削る。変わるなら削らずレイアウトを直す。
サイズを無理に小さくして収めるのも、必要な情報を削って収めるのも、どちらも不正解。

## 10. 文体 — 医学系学会発表の慣例に合わせる

想定聴衆は医学系学会発表の慣例に慣れた人。その読み方に合わせ、スライドは「事実の提示」、
解釈は「口頭」という役割分担にする。

### タイトルは簡潔な名詞句

- ✅ 「生成AIの医学教育への導入状況」「介入群と対照群の比較」「今後の課題」
- ❌ 文で終わる（「生成AIは医学教育に広く導入されている」「対照群より有意に改善した」）
- ❌ 問いかけ・キャッチコピー（「AIは教育を変えるのか？」「今こそ変革を」）
- 見出し（カードの heading / セクション見出し）も同じ。結論を言いたい場合は本文側に事実として書く。

### スライドには事実を書く。憶測を書かない

- スライド面に置くのは、データ・観察結果・引用・定義・手順など**検証可能な事実**。
- ❌ 推測・意見・評価の語尾: 「〜と思われる」「〜だろう」「〜かもしれない」「〜と考えられる」
  「〜すべき」「〜が望ましい」「〜は重要だ」。これらはスライドから外す。
- 主張の根拠になる事実には `cite` / `cites` を付ける。

### 解釈・示唆は「事実の並べ方」で伝え、言葉にするのは口頭で

- 伝えたい解釈がある時、それを文にしてスライドに書くのではなく、**事実の順序・対比・強調**で
  聴衆が自然にその解釈へ至るように構成する（例: 介入前後の数値を並べる、条件の違う2群を左右に置く、
  該当項目だけ accent を当てる）。
- 解釈そのものを言葉にするのは **`narration`（口頭）** で行う。ノートだけで済む発表なら `notes`。
- スライドに「示唆」「考察」の見出しを立てる場合も、中身は事実（観察された差・先行研究との一致/不一致）
  にとどめ、そこからの推論は口頭で補う。
